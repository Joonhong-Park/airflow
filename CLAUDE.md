# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository overview

Airflow DAGs that periodically merge small files in Impala tables (Spark via Livy → HDFS swap → Impala partition
refresh). Full pipeline description, Variable schemas, and operational procedures live in
[README.md](README.md). Per-directory conventions are in [common/CLAUDE.md](common/CLAUDE.md) and
[merge/CLAUDE.md](merge/CLAUDE.md) — read the relevant one before editing files in that directory.

## Environment & validation

- No local Airflow install, dependency manifest, or test suite — DAGs run on a remote Airflow cluster. There is
  no `airflow dags test` or pytest workflow available here.
- The practical local check is Python syntax/compile validity:
  ```bash
  python3 -m py_compile merge/merge_daily_dag.py merge/merge_monthly_dag.py common/*.py
  ```
- The `livy` package (`LivyBatch`, `SessionState`) and the `alarm_wrapper` module (`from alarm_wrapper import
  send_alarm`) are not present in this repo — they're provided by the target Airflow environment. Import errors
  for these when run locally are expected and not a bug.

## Big-picture architecture

### Pipeline (per table, per run)

```
Impala(base) → Spark(Livy) 병합 → HDFS temp 저장
    → HDFS swap(base ↔ temp) → Impala partition refresh → after_count 검증
```

Each table runs as a fixed task chain inside a `task_group`:
`get_metadata_task → impala_health_check_task → log_before_count_task → livy_task → get_partitions_task → swap_refresh_task`

### Two independent DAG families, one shared shape

- `merge/merge_daily_dag.py` and `merge/merge_monthly_dag.py` implement the same pipeline shape but **must not
  import each other**. Shared constants and helpers (`DOMAIN_PATH_MAP`, `pg_conn_id`, `base_cluster`,
  `dag_failure_alarm`, the task implementations themselves) are intentionally duplicated in both files — when
  changing one, check whether the other file needs the matching change.
- Daily merges a single date (`days_ago` → `target_date`). Monthly merges a whole month (`months_ago` →
  `start_date`/`end_date`), then dynamically expands `swap_refresh_task` per-date via `.expand_kwargs()` over
  `get_partitions_task`'s grouped output.
- Both files `sys.path.insert(...)` to import from `../common` (`postgres_wrapper`, `impyla_wrapper`,
  `livy_wrapper`) plus the external `alarm_wrapper`.
- Each DAG family is generated by a factory (`create_daily_dag()` / `create_monthly_dag()`). New schedules are
  added as one extra call at the bottom of the file, not by writing new DAG code.

### Data flow & state

- `table_meta` (Postgres, `pg` connection) is the source of truth for each table's db/table name, HDFS
  `save_path`, partition columns, and `domain` (mapped to an HDFS base URL via `DOMAIN_PATH_MAP`).
- `merge_log` (Postgres) records `before_count`/`after_count` per `(table_id, target_date)`. `before_count` is
  written by `log_before_count_task` before Livy runs; `after_count` after the HDFS swap + Impala refresh in
  `swap_refresh_task`. Upserts only touch `before_count` so retries/backfills never reset `after_count`.
- Manifest files written by the Spark job under `{temp_path}/manifest/*.json` are the handoff between
  `livy_task` and `get_partitions_task` — one JSON object per line, partition-column order preserved.
- `refresh_flags` Airflow Variable gates which Impala clusters get health-checked and refreshed;
  `impala_health_check_task` fails the whole `table_group` if any active cluster fails its check.

### Retry/idempotency design

- `swap_refresh_task` checks whether the `temp` HDFS path still exists to decide if a previous attempt already
  completed the swap — this is what makes retries safe.
- HDFS swap order is `base → backup`, then `temp → base`. On failure it attempts a `backup → base` rollback and
  logs manual-recovery commands if that also fails.
- Impala partition refresh runs per-cluster via `ThreadPoolExecutor`, each partition retried up to 3 times.
  `after_count` must match across all refreshed clusters, or the task raises a retryable `AirflowException`.

## Conventions worth knowing

- Airflow connections: `pg` (Postgres), `cluster1` (base Impala cluster for counts), `livy_cluster` (Spark
  submission), plus other Impala clusters referenced via `refresh_flags`.
- `impyla_wrapper.impala_query` returns `None` on failure and never raises — callers must check for `None`.
  `postgres_wrapper.postgres_query` raises on failure — callers use try/except.
- Currently targets Airflow 2.x (pendulum 2). Known Airflow 3 deltas are marked inline with
  `# TODO(Airflow 3): ...` / `# Airflow 2→3:` comments at the call sites (e.g. `in_timezone()` → `in_tz()`,
  `max_active_tis_per_dag` → `max_active_tis_per_dagrun`).
- New DAG groups get their own subdirectory with a `CLAUDE.md`; shared wrappers go in `common/`.
